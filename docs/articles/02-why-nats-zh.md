# 为什么 A 股数据用 NATS 推送而不是 REST 轮询

> 架构差异化文章 —— 和《用 MCP 把 A 股实时行情接进 Claude / Cursor》配对使用。

---

## 一句话结论

**REST 轮询是「我问你答」，NATS 推送是「你变了告诉我」。** 对 A 股这种
需要实时性、有 Level-2 十档盘口、有 DDX 大单的市场，推送不是锦上添花，
是刚需。

---

## REST 轮询的三个死穴

### 1. 实时性是伪命题

REST 的实时行情本质是「最近一次轮询的结果」。轮询间隔 3 秒，你的数据
就滞后 3 秒。A 股一天 4 小时交易，3 秒 × 480 分钟 = 24 分钟的累积滞后窗口。

更糟的是：**你不知道自己滞后了多少。** REST 返回的时间戳是服务器收到
请求的时间，不是数据产生的时间。

### 2. Level-2 是带宽黑洞

A 股 Level-2 有十档买卖盘。全市场 5000 只股票 × 10 档 × 买/卖 =
10 万个数据点。REST 轮询要每只股票分别请求，要么轮询间隔拉长（漏数据），
要么请求量爆炸（被限频）。

NATS 订阅一个 topic `l2.depth.*`，全市场 L2 数据主动推送到你，不需要
逐只请求。

### 3. DDX 大单会漏

DDX（大单跟踪）的价值在于**捕捉瞬间**。REST 轮询在两次请求之间发生的大单
流入，你完全看不到 —— 你只知道「现在 DDX 是多少」，不知道「中间发生了什么」。

推送模式下，DDX 数据一产生就到你手上。

---

## NATS 在这里做了什么

PandaStock 的数据通道分两层：

### 请求/响应（点查）

```
客户端 → NATS subject "ChOneStockReal" → 服务端 → 响应
```

一次请求，一次响应。适合单只股票查询、K 线拉取、资讯获取。176 个服务端
接口都是这个模式。

### 发布/订阅（推送）

```
服务端 → NATS subject "chStockReal" → 所有订阅者
```

全市场实时行情、L2 盘口、DDX 数据，服务端一产生就推给所有订阅者。客户端
不需要轮询，不需要问「现在什么价」。

**关键设计**：请求/响应和发布/订阅跑在同一个 NATS 集群上，不需要两套
系统。一个客户端可以同时做点查和订阅。

---

## 和 REST 的实际对比

| | REST 轮询 | NATS 推送 |
|---|---|---|
| 实时行情 | 轮询间隔决定滞后 | 数据产生即推送 |
| Level-2 | 逐只请求，带宽爆炸 | 一个 topic 全市场 |
| DDX 大单 | 两次轮询之间会漏 | 不会漏 |
| 客户端负担 | 要管理轮询定时器 | 订阅即可，事件驱动 |
| 扩展性 | 5000 只股票 = 5000 个请求 | 与股票数量无关 |
| 适合场景 | T+1 历史数据、批量回测 | 盘中实时、L2、DDX |

---

## 不是所有数据都该推送

历史 K 线、基本面、财报这些 **T+1 数据**，REST 反而更合适 —— 一次请求
返回一批数据，没有实时性要求，轮询开销为零。

所以 PandaStock 的设计是**混合**：

- **历史/列表/资讯** → 请求/响应（REST 式思维，一次拿一批）
- **实时/L2/DDX** → 发布/订阅（推送式思维，事件驱动）

两层跑在同一个 NATS 上，客户端用同一套连接。

---

## 对 AI Agent 的意义

MCP 工具的调用模式天然是请求/响应（Agent 问 → 工具答）。但 Agent
处理的很多场景需要**持续感知**：

- 「监控 600519，涨到 3000 就提醒我」—— 需要后台订阅，不是轮询
- 「今天哪些股票 DDX 异常」—— 需要实时流，不是快照

如果 MCP 工具背后是 REST 轮询，Agent 的「监控」需求会变成「每 3 秒调一
次工具」—— 低效且不准确。如果背后是 NATS 推送，Agent 可以真正地
「订阅」，数据变了才行动。

这是 PandaStock 选择 NATS 而不是 REST 包装层的根本原因。
